| R-01 | Critical | freeswitch/crm-recording.dialplan.xml > recordingKey set action, and public/app.html > call button handler | The call-to-recording mapping (FR2.2) is never actually connected. The backend derives a `recordingKey` at initiate time and names its download lookups by it (`<key>-rm.wav`, `<key>-kh.wav`, `<key>.wav`), but nothing sets that key on the FreeSWITCH channel for a MicroSIP-placed call. The frontend dials via the Node MicroSIP route passing only the phone number, so FreeSWITCH has no way to learn the key and the dialplan falls back to `${uuid}`. Every real recording is therefore named by a UUID the backend never looks for, and the download step returns "not ready" indefinitely — the exact random-UUID problem FR2.2 exists to remove. | Define and wire the one path that carries the backend's `recordingKey` onto the recorded channel (for example: originate with `recordingKey` exported as a channel variable, an inbound SIP header the dialplan reads, or a key format FreeSWITCH can derive from the dialed number that the backend reproduces). Document that path in the setup guide so the demo records to a name the backend can fetch. | New |
| R-02 | Major | aidlc/spaces/default/intents/261008-crm-call-assistant/construction/code-generation/code-generation-plan.md > Step 4 (per-leg naming) vs freeswitch/crm-recording.dialplan.xml > primary record_session action | The per-leg path the code treats as primary (`<key>-rm.wav` / `<key>-kh.wav`, which gives exact RM/KH labeling with no diarization) is only the commented-out ALTERNATIVE in the dialplan; the active config writes a single stereo `<key>.wav`. A single stereo file is one audio stream, so `RecordingService` will take the single-file branch and `SttService` will depend on provider diarization — but the default `WhisperHttpSttClient` targets a stock Whisper transcription endpoint that returns no `speaker` field, so every turn collapses to the same label. The headline FR4.2 capability (caller/callee separation) will not work on the default happy path. | Make the active dialplan match the primary code path (write the two per-leg mono files), or document that caller/callee separation requires a diarization-capable STT endpoint and that the shipped stereo-single-file + stock-Whisper combination will not separate speakers. | New |
| R-03 | Major | backend/src/main/java/com/mb/callassistant/service/RecordingService.java > tryFetch, and backend/src/main/java/com/mb/callassistant/service/CallPipelineService.java > runPipeline | The pipeline runs once, synchronously, the instant `/ended` is received, but a FreeSWITCH `.wav` is typically not flushed to its final location until shortly after the leg hangs up. `tryFetch` treats a 404 (and any transport error) as "leg absent" and returns null, so a recording that is merely a second late is indistinguishable from one that will never exist: the pipeline immediately sets FAILED/RECORDING_NOT_READY and never retries. The frontend polls `GET /api/calls/{id}` for a status the backend will not change on its own, so the "results when ready" promise (FR1.3) depends on a race the code does not manage. | Add a bounded retry/backoff (or a re-trigger path) between call-end and the download so a not-yet-written recording is retried rather than failed on first miss, and distinguish "not ready yet, keep polling" from "permanently absent." | New |

| R-06 | Major | freeswitch/crm-recording.dialplan.xml > B-leg (KH) recording action | The customer leg is recorded with `execute_on_answer=uuid_record ${uuid} start ...-kh.wav`, where `${uuid}` is the A-leg (RM) channel's own UUID. `uuid_record <uuid>` records the channel named by that UUID, so this re-records the RM/A-leg channel into `-kh.wav` rather than the bridged customer channel. Both files would then carry the same (A-leg) audio, defeating the exact RM/KH speaker separation this per-leg path exists to provide (FR4.2). The customer leg's own UUID is a different value not known at this point in the A-leg dialplan. | Record each leg with the application that captures its own channel audio — e.g. `record_session` with `RECORD_STEREO`/`RECORD_BRIDGE_STEREO_SWAP` to get caller and callee on separate channels of one file, or bind the B-leg recording to the bridged channel's own UUID (via `bridge`/`origination`/`api_on_answer` on the far leg) rather than reusing the A-leg `${uuid}`. Verify on the box that `-rm.wav` and `-kh.wav` contain different audio before relying on per-leg attribution. | New |
| R-07 | Minor | backend/src/main/java/com/mb/callassistant/service/FreeSwitchClient.java > resolveChannelUuid / matchesDestination | UUID resolution matches only on the dialed destination number and then takes the "most recent" entry by walking the list tail-first. Two assumptions are unverified and acknowledged as guesswork in code-summary.md: (a) that `GET /api/calls` returns channels in a stable oldest-first order, and (b) the exact JSON field names (`destination_number`/`dest`/`callee`/`to`, `uuid`/`call_uuid`/...). If two calls target the same `phone_number` (e.g. two RMs both dialing extension 1001, plausible with FreeSWITCH default users per FR1.2) the resolver can bind the wrong channel's UUID, and if the list order or field names differ it binds none. | For the demo, document the single-concurrent-call assumption and confirm the real `/api/calls` field names and ordering against the live FS REST API during Build and Test; if concurrent same-number calls are possible, narrow the match (e.g. correlate on caller/A-leg or call start time) rather than "newest wins". | New |
| R-08 | Minor | backend/src/main/java/com/mb/callassistant/service/CallService.java > initiate / markEnded (resolution window) | UUID resolution runs as a background poll of up to `resolveMaxAttempts` × `resolveDelayMs` (default 10 × 1000 ms = ~10 s) started at `initiate`, plus one synchronous attempt at `/ended`. A call that connects after that ~10 s window relies entirely on the single `/ended` attempt; a very short call ended before the channel appears in `/api/calls`, or one answered after the window with the `/ended` attempt also missing it, leaves `recordingKey` null and the download fails as `RECORDING_NOT_READY` with no further resolution. | Acceptable for the demo given the retry on `/ended` and the non-terminal not-ready status; optionally extend the resolution window or add a resolution retry on the not-ready path, and note the timing assumption in RECORDING-SETUP.md. | New |
| R-09 | Minor | freeswitch/RECORDING-SETUP.md > 6c. Server block (`location /fs/` proxy_pass) | The nginx `proxy_pass http://127.0.0.1:8080/` example for the FreeSWITCH REST API uses port 8080, which is also the Spring Boot backend's default (`application.yml` `server.port: ${BACKEND_PORT:8080}`). A reader following the guide verbatim on a box that also runs the backend would proxy `/fs/` to the backend rather than to FreeSWITCH. The surrounding prose does say to point it at the real FS REST API host:port, so this is a copy-paste hazard, not a logic error. | Change the example `proxy_pass` port to a clearly non-backend placeholder (or add an inline note that 8080 is only illustrative and must not collide with the Spring Boot port) so the mapping is unambiguous. | New |
| R-10 | Major | backend/src/main/java/com/mb/callassistant/service/CallService.java > markEnded | markEnded runs inside a database transaction and, before that transaction commits, hands the call off to the background pipeline, which immediately re-reads the same call record on another thread. The background thread can read the record before the hang-up changes are saved, briefly seeing the old status and no recording filename. In the demo this usually self-corrects because the pipeline re-reads the latest filename and re-sets the status, but the ordering is a real race rather than a guarantee. | Start the background pipeline only after the hang-up changes are committed (for example, hand off after the transaction completes), so the pipeline always sees the saved record. | New |

A single long-running pipeline is fine for the one-at-a-time demo, but several overlapping calls would each hold a worker thread for the full budget. | Confirm the default pool size and retry budget are acceptable for the demo, or note the one-call-at-a-time assumption alongside the retry settings. | New |

### Summary
